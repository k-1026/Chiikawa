기획 절차서 & 에이전트 구성도

사용자는 오케스트레이터에게만 말하고, 오케스트레이터가 요청을 판단해 서브에이전트에게 일을 나눠요. 결과는 검증을 거쳐 오케스트레이터가 종합해서 돌려줘요. 모든 결정과 진행 상태는 파일에 남아서, 중간에 끊겨도 이어 가고 다음 해에도 다시 읽어요.

① 전체 구조

사용자 창구는 하나예요. 서브에이전트는 사용자에게 직접 묻지 않아요. 오케스트레이터는 매번 결정기록과 진행 상태를 먼저 읽고 시작해요.

1창구는 하나서브에이전트는 정보가 없으면 사용자에게 묻지 않고 "질문 필요: ○○"를 돌려줘요. 오케스트레이터가 모아서 한 번에 물어요.
2게이트는 규칙으로✅ 단계는 LLM 판단에 맡기지 않아요. 00_결정기록에 승인 줄이 없으면 00_진행상태가 다음 단계를 막아요.
3원본은 직접 읽기공통 정보를 메시지로 길게 넘기지 않아요. 각 에이전트가 P0 · Y 등 원본 파일을 직접 읽어요.
4결과는 파일로결과는 파일로 저장하고 요약만 넘겨요. 오케스트레이터 맥락이 넘치지 않게 하려는 거예요.
5단계마다 검사모든 단계는 작업 → 검증을 거쳐야 다음으로 넘어가요. 불통과는 2회까지 재작업, 그래도 안 되거나 심각도 "상"이면 섞지 않고 담당자에게 보고해요.
6기다릴 게 없으면 동시에A·B·C·D·E·F·G는 병렬로 불러요. J 검수(A·F 문구)와 G의 E-5 이어받기처럼 앞 결과가 필요한 건 이어서 불러요.
7날짜는 계산날짜 · 요일 · D-day는 추측하지 않고 date로 계산해요. H 역산 일정(D-180~D+30)이 여기에 걸려요.
8하지 않는 것외부 업체 연락, 계약, 비용 집행, 게시물 발행, 인허가 최종 판단은 하지 않아요. 통계·업체 정보·참여 의사를 지어내지 않아요.

③ 요청 처리 방식 — 모드 3개

오케스트레이터는 먼저 00_진행상태를 읽고 모드를 골라요. 어느 모드든 마지막은 검사 → 종합 → 기록 → 보고예요.

📘 전체 기획 모드

예: "2027 축제 기획안 만들어줘"
S0 직전 결과→S1 조건 ✅→ S2 조사→S3 문제→S4 연도 주제 ✅→ S5 아이디어→S6 평가 ✅→ S7 파트 기획→S8 운영→S9 KPI→ S10 전체 검증·통합 ✅→S11 결과 판정 ✅→↻ 다음 해 S0

순서는 고정. 단계를 건너뛰거나 바꿀 수 없어요. 각 단계 안에서 누구를 부를지만 판단해요. 화살표 하나하나가 "작업 → 단계 검증"을 거쳐요. 게이트는 5개이고, 매번 담당자 확인을 받아요.

⚡ 부분 요청 모드

예: "토론 논제만 다시 짜줘", "예산 다시 계산해줘"
요청 판단→라우팅 표 조회→ 필요한 서브에이전트만 호출→관련 Checker→종합 · 보고→영향 파트 ⚠ 표시

호출은 자율. 앞 단계 산출물이 없으면 가정값을 적고 진행해요. 결과가 다른 파트 값을 바꾸면(예: 부스 수 → 예산) 그 파트 파일에 ⚠를 달고 같이 알려 줘요.
