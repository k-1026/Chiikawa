# 09. 주문·결제 — 코드 명세 (K07 4장 "주문·결제")

> 작성: 2026-11-26 · 설계 허브: [K07](K07_웹기능설계_로그인_주문결제_대기_사전챗봇.md) · 코드: `웹코드/order/order.js` · 부스·메뉴 데이터: `웹코드/data/data2.js`(에이전트가 갱신)

## 1. 하는 일
부스 목록(10미 포장마차 / 7구 맛집) → 메뉴 → 장바구니(부스 단위) → 결제 → 대기번호. 플리마켓·굿즈는 현장 결제만.

## 2. 결제 2안 (2026-11-26 ✅)
| 안 | 내용 | 조건 |
|---|---|---|
| 1안 | **온라인 결제**: 카카오페이 (카카오 계정만) | 카카오페이 제휴 가맹점 필요 |
| 2안 | **웹 주문 접수 후 현장 결제**: 웹에서 주문하면 접수·대기번호는 나오고, 결제는 부스·공통 **오프라인 결제기**에서 | 제휴가 안 될 때, 구글 계정·둘러보기 로그인 후 사용자 |
- **어느 안이든 대기열은 하나**: 결제 방식과 상관없이 같은 부스 대기열에 쌓인다(K10).
- 현장 구두 주문도 직원이 입력해 같은 줄에 선다(K10).

## 3. 입력·출력
- 입력: 부스 id, 메뉴 id별 수량, 로그인 상태
- 출력: 주문 1건 `{ no(대기번호), boothId, lines, total, status }` → K10이 대기열로 관리
- 규칙: 메뉴는 표준어+사투리 병기, 업소는 심사 전 "후보", 10미 메뉴는 7구에서 팔지 않음(P0-3)

## 4. 시험판(모의) vs 실제
| | 시험판 | 실제 |
|---|---|---|
| 결제 | 버튼 1번에 항상 성공 | 서버가 카카오페이 `ready` → 사용자 결제창 → `approve` 순으로 호출 |
| 금액 | 화면 계산 | **서버가 메뉴 가격으로 다시 계산**(화면 값 믿지 않음) |
| 주문 저장 | 브라우저 | Supabase `orders` 표 |

## 5. 필요한 키
| 키 | 위치 | 무료 여부 |
|---|---|---|
| `KAKAOPAY_SECRET_KEY`, `KAKAOPAY_CID` | **서버만** | **테스트 CID `TC0ONETIME`은 무료·돈 안 나감.** 실결제는 사업자 제휴 필요 → MVP 불가 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버만 | 무료 플랜 |

## 6. MVP에서 못 구하는 것과 대체
- **실결제(제휴 가맹점)**: 못 구함 → 카카오페이 **테스트 모드**로 흐름 확인, 최종 운영은 2안(현장 결제기)으로 대체 가능.
- 정산 구조는 웹에서 정하지 않음(H-1 소관, ✅ 2026-11-26).

## 7. 기획자 확인 항목 ❓
**확정(2026-11-26)**: 부스 접수 전까지만 사용자 취소, 품절·부스 사정은 환불, 현장 결제는 현장에서 환불. 정산 주체는 웹에서 정하지 않음.
