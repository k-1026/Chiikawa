# 07. 웹 기능 설계 — 로그인·주문결제·대기·사전·챗봇

> 작성: 2026-11-25 · 팀 대화로 확정(결정 ✅) · 기준: K01~K06, P0 V14, 지도 `웹/`·`웹/supabase/`
> **이 문서가 K00~K06의 "안내·시연용 시안(데모)" 전제를 대체해요.** K01~K06의 축제 사실(일정·구역·토론 규칙)은 그대로 쓰고, **웹이 하는 일**은 여기를 따라요.
> 표시: ✅ 확정(대화 결정) / 🟢 지침으로 이미 확정 / 🟡 제안(확인 필요) / ❓ 미정

## 2. 지켜야 할 P0 규칙 (기능 설계의 한계선)
0. **웹은 선택이에요. 웹을 쓰지 않아도 축제에 똑같이 참여할 수 있어요.** (2026-11-25 ✅, P0 "편하게 즐긴다")
   - 주문·결제: 현장 결제로 동일하게 가능. 대기번호는 **현장에서 구두로 안내**(✅ 2026-11-25)
   - 현장 안내·지도 인쇄물은 현장에서 제공. 웹에는 스탬프 메뉴·안내·적립·주문 연동을 제공하지 않음
   - 관객 투표만 예외: 웹 로그인 필요(A-3). 휴대폰 없는 관객은 투표 불가, **현장 대체 수단은 두지 않음**(✅ 우선 이대로)
   - **웹 전용 혜택은 없음**(✅): 웹 사용자에게만 가격·메뉴·보상 우대를 주지 않음. 설문 응답 보상도 없음
   - 외국인 등 카카오 계정이 없는 방문객: **온라인 구매·투표를 제외한 모든 것**을 할 수 있어야 함(✅). → **구글 계정 로그인으로 해결**(✅): 투표·열람은 가능, 구매는 현장
1. 사투리 사용은 **선택**. 표준어 주문·참여도 똑같이 가능 (P0-1 2-1, B-7). 사투리 주문 미션은 혜택만 다르게.
2. 모든 부스 메뉴는 **표준어 + 사투리 병기** (예: "부추전(정구지 지지미)").
3. 개인정보 **최소 수집·동의**: 카카오 로그인에서 받는 항목을 필수 최소로(닉네임 등), 온라인 주문자 정보 동의 (D-6, I-3).
4. 10미 메뉴는 7구 존에서 팔지 않음. 업소는 심사 선정 전까지 "후보".
5. 결제 정산은 H-1 결제·정산 기준 — 정산 주체 ❓.
6. 마스코트는 D-1 검수 (색·설정 변경 금지).
7. 셔틀 문구 넣지 않음, 논제 추천 입력 없음 (K02).

## 2-1. 첫 진입 흐름 (✅ 방향, 세부 🟡)
```
접속 → 카카오 로그인 → (동의: 개인정보·설문) → 간단 설문 → 홈
재방문: 로그인 유지 → 설문 완료자는 바로 홈
```
- 설문은 I-4 **사전 설문**과 연결: 사투리 인식 문항은 **사후 설문과 같은 문장**이어야 비교 가능(P0 7번·I-4). 문항 문장은 J·K·I가 정해야 해요(미확정).
- 설문 응답은 카카오 계정 ID와 분리 저장(통계용), 수집 항목·보관기간을 동의 화면에 표시(I-3).
- 설문 문항 후보(🟡): 거주지(대구·경북/타지역), 연령대, 동반 형태·자녀 나이대(가족 검증), 사투리 접점, 방문 목적. 항목은 최소로.
- 사후 설문(M)은 축제 중·후 같은 문항으로 다시 받음.
- 웹을 안 써도 참여 가능하므로(2장 0번) 로그인 선행의 이탈·배제 부담은 줄어요. 그래도 아래 경고는 웹 안에서 유효해요.
- ⚠️ 로그인 선행은 P0 "편하게 즐긴다"와 부딪힐 수 있어요: 입구에서 이탈하는 방문객이 생기고 카카오 계정 없는 외국인·고령층은 막혀요. 대안 후보 ❓: ①로그인 선행 유지 ②"로그인 건너뛰고 둘러보기"(주문·투표 때만 로그인).

## 6-1. 연도별 변경 구조 (✅ 방향, 세부 🟡)
- **기능은 고정, 내용만 해마다 바뀜.** 화면 문구·일정·구역·부스·논제·혜택 값은 코드가 아니라 **데이터(DB)**로 두고, 기능(로그인·주문·대기·사전·챗봇)은 코드로 둠.
- 순환형 축제 에이전트가 그해 세부지침안을 확정 → 아래 매핑표대로 웹 데이터만 갱신.
| 에이전트 산출(파트) | 바뀌는 웹 데이터 | 비고 |
|---|---|---|
| P0-1·3·4 (개요·장소·시간) | 축제 정보, 구역, 운영시간, 지도 | `웹/대사투웹사이트/README.md` 변경표와 같은 구조 |
| A (토론·골든벨·뮤지컬·NPC) | 프로그램, 일정, 논제·대진표 | 투표 항목도 연동 |
| B (10미·7구) | 부스, 메뉴(표준어+사투리), 가격 | 주문 기능이 읽음 |
| C (플리마켓) | 프로그램 안내 | |
| D (마스코트) | 이미지·소개 | 검수 필요 |
| G-5 (숙박 혜택) | 혜택 안내 | 금액·재고는 해마다 담당자 입력 |
| J (사투리 사전) | 사전·번역기 DB, 챗봇 지식 | |

- 해마다 안 바뀌는 것: 이름(대사투)·큰 콘셉트·핵심 메시지(P0-1 고정). 바뀌는 것: 연도, 세부 콘셉트, 일정, 부스·메뉴, 논제, 혜택 금액.
- 이전 해 데이터 보관은 K파트가 아니라 **전체 순환형 에이전트**가 맡음(✅). 웹은 그해 값만 읽음.
- **웹은 순환형 에이전트가 돌아갈 때 나오는 결과물 중 하나**(✅). 사람 검수 단계는 전체 에이전트의 검수 규칙을 따름. 작업 지시 형식은 K00 5장.

## 6-3. POS 연동 방식 (🟡 제안, 공급사 확인 후 확정)
**1단계: 공통 POS 공급사에 확인**
| 확인 항목 | 이유 |
|---|---|
| 외부 주문을 POS로 넣는 API(주문 등록) 제공 여부 | 있으면 웹 주문이 자동으로 POS에 쌓임 |
| 주문 상태 변경 알림(웹훅) 또는 조회 API | 호출·완료를 웹 대기번호에 반영 |
| 오프라인(인터넷 끊김) 모드, 장애 시 복구 방식 | 야외 축제 네트워크 불안 대비 |
| 부스 수만큼 단말·메뉴 등록 지원 | 업소 100여 곳 규모 |

**2단계: 결과에 따른 분기**
- **API 있음**: 웹 주문 → 자동 POS 접수. 직원 입력 불필요. 대기 순서는 POS 순서 그대로.
- **API 없음(기본 가정)**: 웹 주문이 **부스 태블릿에 알림음과 함께 표시** → 직원이 [접수]를 누르고 POS에 입력 → 같은 주문번호를 POS 영수증에 적음. 이중 입력 부담은 있음(주문 건수 많은 부스는 보조 인력 배치).

**장애 시 대체 절차 (POS 멈춤·인터넷 끊김)**
1. 부스는 **종이 주문표 + 구두 번호**로 전환(오프라인 구두 원칙 그대로).
2. 웹은 해당 부스의 **대기 수·예상 시간을 숨기고** "현장 안내를 따라 주세요"로 표시(잘못된 대기 수 방지). 온라인 주문 접수는 일시 중지 가능.
3. 이미 결제된 카카오페이 주문은 서버에 기록이 남으므로 **주문 목록 인쇄·태블릿 확인**으로 처리.
4. 복구 후 종이 주문을 POS에 일괄 입력, 웹 상태 재개.
5. 부스별 비상 연락처·담당자는 운영 파트(H)와 정함 ❓.

## 6-4. 기획자에게 마지막에 물어볼 사항 (에이전트 최종 단계)
에이전트는 아래를 **임의로 정하지 않고**, 웹 결과물을 낼 때 마지막에 기획자에게 질문으로 남겨요. 답을 받은 뒤 반영해요.
